## 6. Migration — solo quelle mancanti, in quest'ordine

Tutte e due sono additive e idempotenti: il vecchio codice ancora acceso continua a funzionare.

```bash
cd /opt/trainmind/trainmind-app
M=packages/db/prisma/migrations

# solo se plans_trial era vuoto
dc exec -T postgres psql -U trainmind -d trainmind_db -v ON_ERROR_STOP=1 < $M/20261009090000_plans_trial_extensions/migration.sql

# adattamenti AI
dc exec -T postgres psql -U trainmind -d trainmind_db -v ON_ERROR_STOP=1 < $M/20261013090000_adaptation_lifecycle/migration.sql
```

Verifica:

```bash
dc exec -T postgres psql -U trainmind -d trainmind_db -c '\d plan_adaptations'
dc exec -T postgres psql -U trainmind -d trainmind_db <<'SQL'
SELECT status, count(*) AS totale, count("teamId") AS con_squadra,
       count("athleteId") AS con_atleta, count("appliedPlan") AS con_piano_applicato
FROM plan_adaptations GROUP BY status ORDER BY status;
SQL
```

Attesi: `athleteId` senza `not null`; colonne `teamId`, `appliedPlan`, `revertedAt`,
`revertedById`, `supersededById`; le APPROVED con `con_piano_applicato` = `totale`.

Registra le migration (il `migrate` è stato ricostruito al passo 5) e dai i permessi alla console:

```bash
# solo se al passo 6 hai applicato anche quella del 9/10
dc --profile tools run --rm --entrypoint sh migrate -c 'cd packages/db && npx prisma migrate resolve --applied 20261009090000_plans_trial_extensions'

dc --profile tools run --rm --entrypoint sh migrate -c 'cd packages/db && npx prisma migrate resolve --applied 20261013090000_adaptation_lifecycle'

dc exec -T postgres psql -U trainmind -d trainmind_db -c 'GRANT SELECT ON ALL TABLES IN SCHEMA public TO trainmind_reporting;'
```

Se `resolve` risponde `P3017: the migration could not be found`, l'immagine `migrate`
non è stata ricostruita: rifai il passo 5 solo per `migrate`.

## 8. Prova in produzione

Su `https://lab21sport.com/app`, con un account di prova:

1. Login, dashboard.
2. **Adattamenti AI** → Squadra → scegli una squadra: il secondo menu mostra le sessioni
   pianificate da oggi a 7 giorni, la prima già selezionata, e l'avviso sulle metriche di oggi.
3. Genera → Modifica → cambia ripetizioni o recupero → Applica: messaggio "Correzioni applicate".
4. Filtro **Modificato** → riapri la proposta: niente Approva/Rifiuta, si vedono i valori applicati.
5. **Ripristina originale** → conferma: la proposta passa in "Ripristinata".
6. Genera due volte sulla stessa sessione: la prima finisce in "Superata".
7. Apri una sessione **completata**: niente "Aggiungi esercizio", campi disattivati, avviso di sola lettura.

## 9. Se qualcosa va storto

- **API che non parte**: `dc logs --tail=100 api`. Un `Unknown argument teamId` vuol dire
  immagine `api` vecchia: `dc build --no-cache api && dc up -d --force-recreate api`.
- **Tornare indietro**: la migration non va annullata (il codice vecchio regge le colonne
  nuove), ma la pagina vecchia si rompe sulle proposte di squadra, che ora hanno
  `athleteId` NULL. Il ritorno pulito è il ripristino del backup del passo 2, che **perde
  tutto ciò che è stato scritto dopo**:
  ```bash
  dc stop api web
  dc exec -T postgres psql -U trainmind -d postgres -c 'DROP DATABASE trainmind_db WITH (FORCE);'
  dc exec -T postgres psql -U trainmind -d postgres -c 'CREATE DATABASE trainmind_db OWNER trainmind;'
  dc exec -T postgres psql -U trainmind -d trainmind_db < /opt/trainmind/backups/pre_20261013.sql
  ```
  poi si ricarica il codice precedente e si ricostruiscono `api` e `web`.
