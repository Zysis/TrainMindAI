## 3. Schema del database

L'immagine `migrate` congela lo `schema.prisma` al momento del build: va
ricostruita, altrimenti `db push` risponde "Already in sync" senza fare nulla.

```bash
cd /opt/trainmind/trainmind-app
dc --profile tools build migrate
dc --profile tools run --rm migrate pnpm --filter @trainmind/db exec prisma db push --accept-data-loss
```

Verifica che le colonne ci siano davvero:

```bash
docker exec trainmind-postgres psql -U trainmind -d trainmind_db \
  -c '\d field_training_sessions' | grep -E 'availableAthletes|exercises|guests'
docker exec trainmind-postgres psql -U trainmind -d trainmind_db \
  -c '\d field_training_entries' | grep -E 'status|note'
```

Devi vedere `availableAthletes | integer`, `exercises | jsonb`, `guests | jsonb`,
`status | text` e `note | text`.

**Se il servizio `migrate` fa storie**, le due migration sono idempotenti
(`ADD COLUMN IF NOT EXISTS`), quindi si possono applicare direttamente:

```bash
for f in /opt/trainmind/trainmind-app/packages/db/prisma/migrations/2026081910*/migration.sql \
         /opt/trainmind/trainmind-app/packages/db/prisma/migrations/2026082009*/migration.sql; do
  docker exec -i trainmind-postgres psql -U trainmind -d trainmind_db < "$f"
done
```

## 4. Ricostruire API e web

`--no-cache` è obbligatorio: dopo un tar, Docker considera spesso il layer
`COPY . .` già in cache e ti servirebbe il codice vecchio.

```bash
dc build --no-cache api
dc up -d --force-recreate api
dc ps            # attendi trainmind-api "healthy"

dc build --no-cache web
dc up -d --force-recreate web
dc ps
```

Il build dell'API stavolta è più lungo del solito: scarica Chromium.

## 6. Se qualcosa va storto

Il rollback del codice è tornare ai file precedenti e ribuildare. Il database
invece va ripristinato dal backup del punto 1:

```bash
gunzip -c /opt/trainmind/backups/NOMEFILE.sql.gz | \
  docker exec -i trainmind-postgres psql -U trainmind -d trainmind_db
```

Le colonne aggiunte sono però tutte additive e con valore predefinito: il
codice vecchio continua a funzionare anche con lo schema nuovo. Se il problema
è nel frontend, basta rimettere i file `.tsx` precedenti e rifare
`dc build --no-cache web`.

## Nota sul PDF

Il renderer aveva un difetto: l'istanza di Chrome veniva memorizzata in una
promise che non veniva mai scartata in caso di errore, quindi dopo un primo
fallimento *ogni* PDF successivo falliva fino al riavvio dell'API. Ora la
promise viene buttata via se fallisce e il browser viene ricontrollato prima
del riuso. Se il PDF continua a non uscire, il messaggio d'errore che compare
nel toast della pagina è ora quello vero dell'API: leggilo prima di indagare.
