## Prima di tutto: perche' non si usa `prisma migrate deploy`

In produzione `_prisma_migrations` ha **22 righe**, la piu' recente
`20260804090000`. In locale le cartelle di migration sono **43**. Sembra uno
scarto di 21 migration da applicare: non lo e'.

Lo schema di produzione e' molto piu' avanti della sua storia. Ha tabelle e
colonne che nessuna delle 22 migration registrate crea — `daily_reports`,
`game_sessions`, `plan_adaptations`, `field_training_sessions`. E' il segno di
un database mantenuto con `db push`: `db push` allinea lo schema **senza
scrivere niente** in `_prisma_migrations`.

La conseguenza e' netta: `prisma migrate deploy` **non si puo' usare**.
Tenterebbe di applicare 21 migration in fila e morirebbe alla prima
`CREATE TABLE` di una tabella che esiste gia'.

Non e' un incidente da riparare: e' la procedura che questo progetto usa da
sempre, ed e' gia' scritta nei deploy precedenti. Lo schema si allinea con
`db push`, e i file `migration.sql` si lanciano a mano con `psql` perche'
contengono **conversioni di dati** che `db push` non conosce e non farebbe mai
(rinomine di tipi evento, ribaltamento della scala wellness, normalizzazione
delle sedi degli infortuni). Sono due cose diverse che vivono nello stesso
file: la parte DDL la fa `db push`, la parte dati la fai tu.

Tutte le migration sono idempotenti, comprese le due nuove: rilanciarle non fa
danni. **L'unica eccezione e' segnalata al punto 6**, la conversione della scala
wellness, che si autoprotegge con una tabella di controllo.

## 3. Il calendario, PRIMA di `db push`

**Questo passo va fatto per primo, ed e' l'unica differenza di ordine rispetto
ai deploy precedenti.**

`schema.prisma` dichiara `CalendarEvent.organizationId` obbligatoria. Se
`db push` arrivasse per primo, dovrebbe aggiungere una colonna `NOT NULL`
senza default a una tabella piena di righe: o fallisce, o — con
`--accept-data-loss` — te la porta via. La migration invece crea la colonna
annullabile, la popola dall'organizzazione di chi ha creato l'evento, assegna
all'Under 14 gli eventi senza squadra, e **solo dopo** mette il vincolo. Quando
`db push` guarda, trova gia' tutto a posto e non tocca niente.

```bash
cd /opt/trainmind/trainmind-app
docker exec -i trainmind-postgres psql -U trainmind -d trainmind_db -v ON_ERROR_STOP=1 \
  < packages/db/prisma/migrations/20260902170000_calendar_event_organization/migration.sql
```

Deve finire con `NOTICE: calendar_event_organization: vincolo creato.`

Se invece si ferma con

```
ERROR: calendar_event_organization: N eventi senza organizzazione.
```

vuol dire che ci sono eventi il cui creatore non esiste piu'. **Non forzare**:
guarda quali sono con la query che l'errore stesso ti stampa, decidi a chi
assegnarli, e rilancia. La migration e' idempotente, ripartire e' gratis.

Controllo:

```bash
P="docker exec trainmind-postgres psql -U trainmind -d trainmind_db"
$P -c 'SELECT count(*) AS senza_org FROM calendar_events WHERE "organizationId" IS NULL;'
$P -c 'SELECT o.name, count(*) FROM calendar_events ce
       JOIN organizations o ON o.id = ce."organizationId" GROUP BY 1 ORDER BY 2 DESC;'
```

## Dopo il deploy: allineare la storia delle migration

Facoltativo, ma conviene farlo una volta e chiuderla. Oggi
`_prisma_migrations` si ferma al 4 agosto mentre lo schema e' al 3 settembre:

for m in 20260819100000_field_training_exercises 20260820090000_field_training_roster \
         20260823090000_calendar_event_types 20260823120000_exercise_categories \
         20260823140000_metric_type_names 20260824090000_injury_onset \
         20260824100000_injury_seed_types 20260824120000_wellness_scale_flip \
         20260824140000_session_attendance 20260826090000_team_logo \

Da fare **solo alla fine**, e solo se i punti 4 e 5 sono andati a buon fine:

la lanci su una migration che in realta' non e' passata, il prossimo deploy la
salterebbe.
