## 3. Schema del database

L'immagine `migrate` congela lo `schema.prisma` al momento del build: va
ricostruita, altrimenti `db push` risponde "Already in sync" senza fare nulla.

```bash
cd /opt/trainmind/trainmind-app
dc --profile tools build migrate
dc --profile tools run --rm migrate pnpm --filter @trainmind/db exec prisma db push --accept-data-loss
```

Verifica che le colonne nuove ci siano davvero:

```bash
docker exec trainmind-postgres psql -U trainmind -d trainmind_db \
  -c '\d field_training_sessions' | grep -E 'trainingSessionId|durationMinutes|sessionRpe'
docker exec trainmind-postgres psql -U trainmind -d trainmind_db \
  -c '\d field_training_entries' | grep -E '^ rpe'
docker exec trainmind-postgres psql -U trainmind -d trainmind_db \
  -c '\d training_sessions' | grep detailedByAttendance
docker exec trainmind-postgres psql -U trainmind -d trainmind_db \
  -c '\d injuries' | grep onset
```

Attese: `trainingSessionId | text`, `durationMinutes | integer`,
`sessionRpe | integer`, `rpe | integer`, `detailedByAttendance | boolean`,
`onset | text`.

## 4. Migrazioni dei dati

Tutte e nove sono **idempotenti**: rilanciarle non fa danni. Le due del 19–20
agosto sono già in produzione e diventano no-op.

```bash
cd /opt/trainmind/trainmind-app/packages/db/prisma/migrations
for f in 2026*/migration.sql; do
  echo "── $f"
  docker exec -i trainmind-postgres psql -U trainmind -d trainmind_db \
    -v ON_ERROR_STOP=1 < "$f" || echo "!! FALLITA: $f"
done
```

Sulla wellness devi leggere `NOTICE: wellness_scale_flip: applicata.`
Se leggi `già applicata, non faccio nulla` significa che era stata lanciata
prima: **non insistere**, la conversione è simmetrica e un secondo giro
riporterebbe i dati com'erano.

Controllo:

```bash
docker exec trainmind-postgres psql -U trainmind -d trainmind_db \
  -c 'SELECT name, applied_at FROM "_trainmind_data_migrations";'

# nessun tipo evento vecchio deve sopravvivere
docker exec trainmind-postgres psql -U trainmind -d trainmind_db \
  -c "SELECT type, count(*) FROM calendar_events GROUP BY type ORDER BY 2 DESC;"
```

Nella seconda query non devono comparire `field_training` né `training`.

## 5. Ricostruire i container

`--no-cache` è obbligatorio: dopo un tar, Docker considera spesso il layer
`COPY . .` già in cache e ti ritroveresti il codice vecchio.

```bash
cd /opt/trainmind/trainmind-app

dc build --no-cache api
dc up -d --force-recreate api
dc ps                      # attendi trainmind-api "healthy"

dc build --no-cache web
dc up -d --force-recreate web

dc build --no-cache athlete
dc up -d --force-recreate athlete

dc ps
```

Il container **athlete** va ricostruito anche se sembra scollegato da queste
modifiche: la scala wellness vive anche nel suo form. Saltarlo significa avere
i preparatori su una scala e gli atleti sull'altra, senza nessun errore visibile.

## 6. Verifiche

```bash
curl -s https://api.trainmind-app.com/api/v1/health
dc logs --tail 50 api | grep -i error
docker exec trainmind-api chromium-browser --version   # per il PDF dei report
```

Dal browser su `https://trainmind-app.com/app`:

1. **Calendario** → crea un *Allenamento Basket* → pulsante **Presenze & Esercizi**.
   Semafori cliccabili, RPE per giocatore, un esercizio cronometrato,
   **Completa Sessione** senza errori. L'evento deve diventare **verde**.
2. **Analisi → Presenze**: i giocatori di quella seduta con % e carico.
3. **Analisi → ACWR** filtrando su uno di loro: il carico della seduta deve
   comparire **una volta sola**. È il controllo più importante di tutto il deploy:
   se è doppio, il doppio conteggio è tornato.
4. **Wellness**: valori bassi rossi, alti verdi, legenda coerente. Il periodo
   predefinito è 30 giorni, allarga le date se la tabella sembra vuota.
5. **Infortuni**: menu Tipo con cinque voci, Insorgenza, Localizzazione scrivibile.
6. **Report**: testi in italiano, menu Atleta, **Scarica PDF** che apre un file.
7. **PWA atleti**: un questionario wellness nuovo, poi ricontrolla il punto 4 —
   i due lati devono raccontare la stessa cosa.

## Se qualcosa va storto

**Rollback del database** (l'unico irreversibile è il punto 4):

```bash
ls -lh /opt/trainmind/backups | tail -3
# poi il ripristino come da GUIDA_AGGIORNAMENTI.md
```

**Rollback del codice**: i file vecchi non sono salvati da nessuna parte, quindi
prima del punto 2 conviene:

```bash
tar -czf /opt/trainmind/backups/code-$(date +%F).tar.gz \
  -C /opt/trainmind trainmind-app/apps trainmind-app/packages trainmind-athlete/src
```

**Il build del web esaurisce la memoria**: succede sui VPS piccoli. Ferma
`ai-service` durante il build e riavvialo dopo.
